aredn-traceroute hostname resolution

How hop display names are filled when traceroute omits a hostname.

contrib/aredn-traceroute resolveDisplayHostname
Current behavior Names come from traceroute, hop sysinfo, or previous-hop LQM (with mesh-hostname refresh when a tunnel IP fetch fails). Path metric uses local Babel host routes; Babel dumps do not carry hostnames.

Current pipeline

Stock traceroute runs first; enrichment is sequential. Type/cost use previous-hop LQM; path metric uses local Babel host routes. Name resolution reuses the same sysinfo/LQM cache.

Important follow-on in enrichHop

After a mesh name is learned (especially from previous LQM), if the hop was only fetched by numeric traceroute IP, enrichment re-fetches http://{name}/a/sysinfo?lqm=1 and rebinds the cache entry. That improves later LQM lookups and can upgrade the displayed name to sysinfo’s node field. Unreachable hops (* * *) are not named or enriched.

When names stay unresolved

Tunnel / WG hop IPs

Traceroute shows 172.31.x (or similar). Sysinfo on that IP often fails or returns an LQM that does not index the next hop until refreshed via mesh hostname.

Prev LQM miss

findNeighbor only matches tracker.ip / canonical_ip / hostname. If the ICMP address is not those fields, previous-hop naming fails even when the node is known elsewhere.

No local reverse index

Failed sysinfo is cached with no retry. mesh.getNodeList is used for destination metric IP only — not as an IP→name fallback for hop display names.
